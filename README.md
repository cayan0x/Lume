# Lume · 微光

**不替模型思考，只让它手边的事实到位。**

给 DSH Desktop 加四样东西——三层能力，加一块仪表盘：

| 层         | 管什么         | 一句话                                                             |
| ---------- | -------------- | ------------------------------------------------------------------ |
| **纪律层** | 这一轮该怎么干 | 判断请求类型、划清"能不能动手"的边界、交付前对账                   |
| **方法层** | 干活的产出物   | 契约 / 改动台账 / 假设台账 / 设计决策 / 项目知识——可检查、可跨会话 |
| **仪表盘** | 到底有没有用   | 路由判定、触发器命中、外部结果信号落盘，`lume_metrics` 随时可查    |
| **人设层** | 用什么风格说话 | 从真实素材蒸馏具名角色，长期记忆与风格随对话演进                   |

约束**按需注入**：闲聊轮不会背上整份工作协议的成本。人设只影响自然语言表达，不介入代码、命令与工具调用的结果——你选"不使用人设"时，纪律层照样生效。

## 摘要

**在会话里补上"事实到位"这一步。** 它不替模型思考，只让模型手边的事实到位；约束按需注入，闲聊轮不额外加 token。（[插件市场简介](docs/hub-registration.md)是本段的**精简版**——市场只放一句话定位与四组短句，细节留在本文。）

- **纪律层**：按这一句话加最近几轮轨迹判定请求类型（问答 / 查找 / 讨论 / 诊断 / 执行）并划清边界——问答轮不改文件、诊断轮不越权修复；引用本次没打开过的代码行、对没见过的符号下否定断言、需求条目与交付物对不上、把「我没查」包装成「待你定」，都会被当场点出；上下文占用到 75% / 90% 预警并导出结构化会话记忆（目标 / 已拍板 / 未决 / 关键定位），新会话开局注入，续接一句「继续」即可；历史会话（含已撑满聊不动的）启动时自动补蒸馏出跨会话知识，幂等不重复；**输出是给人看的**——从文档或代码搬来的代号、字段名、编号（`P0`、`user_id` 这类）首次出现要用一短句说明它是什么，讲解只答三问（做了什么 / 凭什么说它对 / 还剩什么风险）。
- **方法层（可检查的产出）**：任务契约（目标 / 范围 / 数量先估后回填 / 完成判据 / 非目标）、改动台账（每处改动自动入账并记下验证方式，未验证的条目在交付时点出）、假设台账（含已排除项；下结论必须带证据、裁决方式与反例检查；**验证没通过时插件自动入账一条**，不依赖模型主动调用）、设计决策（决策点 / 选择 / 放弃理由 / 影响面）、按工作目录跨会话累积的项目知识（带编号、可点名删除，只收句子并拦截密钥）。
- **行为触发器（按轨迹纠偏，不看措辞）**：撒网不收敛、连写不验、死路重撞、契约缺失、设计缺失、假设过期、判据漂移、知识未记——每条带具体数字，同类两轮内不重复；另有一条输出侧的**讲人话**（回复里甩了没解释的代号时顶一句，每会话一次）。
- **仪表盘**：路由判定、触发器命中、块装配与外部结果信号写本机 `lume-metrics.jsonl`，`lume_metrics` 可查触发器效能（口径为命中后 3 轮内出现真验证命令或载具从无到有，明确标注观察性；无机械口径的标未判定且不计入分母）。
- **人设层**：从聊天记录、小说、剧本、人物设定文档蒸馏具名角色（语气、口头禅、回复篇幅锚定真实素材统计）；以人设为键的长期记忆，以及 30 天后自动过期的临时记忆；纠正自动转风格约定、认可的回复摘录为语料；切换人设后按签名词做词法泄漏检测；记忆星图可视化与角色卡导出导入。

## 它解决什么问题

_（下面用一个跟你业务无关的小例子：一个自己写着玩的跑步记录 App——单页前端加一个本地 SQLite。）_

同一个需求：「给跑步记录加个『配速』列，历史数据也要补算」。

**没有 Lume**：它直接改了列表页那个表格。你问"迁移脚本写了吗"，它说"已处理"——但它从没打开过建表那一份。你出门跑了半小时步，回来换个窗口继续，它又问你"这个项目怎么启动"。上下文撑满以后，进度就留在那个窗口里了。

**有 Lume**：

- 开工前把你的原话**逐字**记下来，并落一份契约：目标、范围、**数量先估**（探索后回填实际值）、完成判据、非目标；
- 每处改动**自动**进台账（不用它自觉调用工具），交付时把**还没验证的条目**列出来，而不是说一句"已完成"；
- 它引用了没打开过的代码行、对没见过的符号断言"不存在"、把两个需求数成三个、把"我没查"包装成"待你定"——都会被当场点出来；
- 下结论（confirmed / excluded）要过闸：证据、裁决方式、反例检查三项缺一不可；
- 换个窗口说一句"继续"，它带上目标、已拍板、未决、关键定位接着干；
- 觉得"好像没起作用"时，有数据可看：`lume_metrics` 会告诉你这一路的判定、命中与纠正率。

**它不做的事**：

- 不偷偷改文件——问答轮不改文件，诊断轮不越权修复，只有执行轮才动状态；
- 不发起网络请求——除了调用你自己配置的模型档做记忆提取、反思与人设蒸馏；
- 不给闲聊加固定开销——协议与台账是按需注入的；
- 不替你下结论——机械判据只保证"有没有证据"，判断对错仍在模型自己。

## 安装与升级

前置：已安装 DSH Desktop。

```bash
# npm（推荐）
dsh plugin add lume-dsh-plugin

# GitHub（备选）
dsh plugin add github:cayan0x/Lume#v<版本>   # 例如 v0.8.2

# 指定版本 / 最新
dsh plugin add lume-dsh-plugin@<版本>       # 例如 0.8.2
dsh plugin add lume-dsh-plugin@latest
```

**升级**：重复执行同一条命令即可。若当初是用**本地源码目录**装的（依赖里是 `link:`），在源码目录执行：

```bash
git pull && npm install --legacy-peer-deps && npm run build
```

**装完必须完全重启 DSH（含托盘进程）**——插件在宿主启动时加载，DSH 没有热重载。

## 一、纪律层：这一轮该怎么干

### 1.1 先判类型，再划边界

每一轮先用**这一句话 + 最近几轮轨迹**判定请求类型，判定结果与命中的判据都写进注入块（也进度量）：

| 模式     | 允许做什么                                                                      |
| -------- | ------------------------------------------------------------------------------- |
| **问答** | 直接回答；只读核实该做就做，不改文件、不替你做决定                              |
| **查找** | 收集并区分已知 / 未知 / 推断；未经授权不改外部状态                              |
| **讨论** | 比较选项、取舍与风险；不把探讨中的方案当成已定方案                              |
| **诊断** | 说明现象、证据、根因与验证办法；除非你明确要求修复，不越权动手                  |
| **执行** | 确认目标与完成标准，做最小变更；交付时列清已完成 / 已验证 / 未验证 / 残留副作用 |

轨迹只在**证据足够**时补判：纠正后按被纠正前那句话重算、在途任务对承接式追问有粘性、连问两句不算任务；带了疑问特征的句子一律不抬档。证据不足时回落到单句判定，绝不猜。

进入执行后还有阶段推进（answer → research → discuss → diagnose → execute → verify → deliver），阶段决定这一轮是"先给方案"还是"可以动手"。

### 1.2 证据核对：该拿事实说话的地方

| 核对           | 什么时候响                                             | 每会话上限 |
| -------------- | ------------------------------------------------------ | ---------- |
| **引用核对**   | 回答里写了 `文件:行`，但这段本次没打开过               | 3          |
| **断言核对**   | 对没见过的符号下"没映射 / 不存在 / 不支持"这类否定断言 | 2          |
| **需求漂移**   | 有契约在手，进展却偏离了契约的判据（含压缩之后）       | 2          |
| **覆盖核对**   | 写出文档产物之后：把需求原句与交付物里的句子并列对账   | 2          |
| **提问核对**   | 一轮抛出超过 2 条「待你定」，或问题带着"我没查 / 我猜" | 2          |
| **载具缺口**   | 已经动了代码，但契约与设计都还空着                     | 2          |
| **上下文预警** | 上下文占用到 75% / 90%                                 | 3          |
| **度量自校**   | 本会话路由被反复纠正（≥2 次）                          | 2          |

上限不是"省着用"，是**防噪音**：同一个提醒反复顶，模型会开始躲词而不是解决问题。所以每个槽有自己的用量上限与冷却，多数槽还有"清空条件"——你补上了它就不再提。

### 1.3 行为触发器：不看你怎么说，看轨迹

协议文本管不了"在压力下不执行"——实测症状是连续几十次广度探查不收敛、连续十几次改动不验证、在同一个坏环境上撞十几次。这类症状是**轨迹**的，所以判据也在轨迹上：

| 触发器              | 判据（可配阈值）                          | 命中后给什么                                                           |
| ------------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| `converge`          | 连续只读探查 ≥ 12 步仍无产出              | 停止撒网，先复述链路并落台账                                           |
| `verify-as-you-go`  | 连续改动 ≥ 4 步（或台账未验证项 ≥ 4）     | 先跑一次最小验证，再把台账推进到 verified                              |
| `dead-path`         | 同一验证连续失败 ≥ 3 次                   | 环境类给"验证降级阶梯"，其余要求先分清是哪类原因，并把结论记进假设台账 |
| `hypothesis-stale`  | 诊断轮出现验证失败，但假设台账没更新      | 把失败归因落成假设，标出下一步验哪条                                   |
| `contract-missing`  | 已经动手，但还没写契约                    | 补一份契约（目标 / 范围 / 数量 / 判据 / 非目标）                       |
| `design-missing`    | 设计型任务摸了 ≥ 6 处代码仍无设计记录     | 写`lume_design`：决策点 / 选择 / 放弃理由 / 影响面                     |
| `criteria-drift`    | 有契约，且距上次对账 ≥ 3 轮（或刚压缩过） | 拿契约逐条对账，防止判据随进展漂移                                     |
| `knowledge-capture` | 工具步数 ≥ 20 且本会话还没提醒过          | 若有稳定事实（命令 / 链路 / 约定 / 死路）就记下来                      |

规矩：一次只顶**一条**（按紧急度排序，同时堆三条会互相稀释）、每类每轮最多一次、同类两轮内不重复、文本里带**具体数字**（"已连续 14 次只读探查"）——让提醒可被核对，而不是空洞训话。

## 二、方法层：把量化落成能检查的产出

### 2.1 十个工具

模型丢的通常不是"不知道要量化"，而是**没有一个地方放量化结果**。任务侧七个：

| 工具                  | 做什么                                                                                |
| --------------------- | ------------------------------------------------------------------------------------- |
| `lume_contract`       | 任务契约：目标 / 范围 / 数量（先估后回填）/ 完成判据 / 非目标 / 待确认                |
| `lume_change`         | 改动台账：改什么 → 为什么 → **怎么验证的** → 状态；只推进状态时可只传 target + status |
| `lume_hypothesis`     | 假设台账：open / testing / confirmed / excluded；含被推翻的已排除项                   |
| `lume_design`         | 设计决策：决策点 → 选择 → 被放弃的方案与理由 → 影响面                                 |
| `lume_project_note`   | 记一条稳定的项目事实（按工作目录跨会话累积）                                          |
| `lume_project_forget` | 按编号删掉一条过时或记错的项目知识                                                    |
| `lume_metrics`        | 读运行时度量：路由判定 / 外部结果信号 / 块装配 / 触发器效能                           |

人设侧三个：`lume_remember`（一条持久事实）· `lume_update_style`（一条风格约定）· `lume_create_persona`（访谈后新建人设）。

### 2.2 契约长这样

```
lume_contract({
  goal: "跑步记录新增「配速」列：列表展示 + 历史记录补算 + 导出可用",
  scope: "run_record 表与迁移脚本、列表页组件、CSV 导出",
  expectCount: 6,            // 先估：6 个改动点，探索后回填实际值
  criteria: ["新记录能自动算出配速", "历史记录已补算", "导出的 CSV 里含配速列"],
  nonGoals: ["不改 CSV 既有的列顺序", "不动手机端的同步逻辑"],
  open: []                   // 默认 0 个待确认——能自己核实的不许抛回来
})
```

### 2.3 核心机制不靠模型自觉

这是刻意的取舍：只靠提醒的机制会退化成"提醒了很多次，一次都没落地"。所以这些是插件**机械完成**的，模型调用工具只是为了补充细节：

- **改动台账自动入账**：`mutate` 类工具一被调用，就从入参里记一条（标注"（自动）"）；
- **需求锚点**：用户原话逐字留存，供覆盖核对与漂移检查；
- **项目知识自动沉淀**：不依赖模型调 `lume_project_note`（实测它三次全部落空）；
- **覆盖核对、引用核对、断言核对**：纯词法 + 本会话证据索引，零额外模型调用。

### 2.4 下结论要过闸

假设台账的 `confirmed` / `excluded` 是**裁决**，不是备注：证据（≥8 字，写清观察）、裁决方式（用哪条命令 / 工具、看什么结果）、反例检查（找过哪些反例）三项缺一即拒。证据里出现的路径引用必须**本会话真的打开过**，否则点名报错。

理由很直白：真机里这两个状态曾经只带一句"已验证 / 无"——无法复核的结论，等于把猜测固化成跨轮次的事实。

### 2.5 项目知识：越用越强的那部分

- **按工作目录归属**跨会话累积；需求特有的结论带"（本需求）"标记，只在同一需求内可见，换项目不会串；
- **带编号**，可以在对话里点名删除（`lume_project_forget`）；
- **有形状闸**：只收句子，不收测试输出行、代码片段、表格行、复制粘贴的命令行；宁窄勿宽——宁可漏记，也不要把仓库开发过程的产物灌进知识库；
- **有敏感拦截**：带值的密钥、连接串、私钥一律不入库（项目知识是明文跨会话存储）；
- **历史补蒸馏**：启动时扫最近 7 天的会话（**包括已经撑满、聊不动的那些**）补出跨会话知识，分片执行、幂等不重复。

## 三、仪表盘：它到底有没有起作用

装了约束和提醒之后，最该回答的问题不是"机制在不在"，而是"命中之后行为真的变了吗"。所以 v0.8 起先装仪表盘：

- **记什么**：路由判定（模式 + 命中判据 + 证据来源）、触发器命中（带命中当时的计数器快照）、块装配（留下 / 丢弃 / 字符数 + 本轮加权了哪几条条款）、每轮状态快照（契约 / 设计 / 台账 / 假设）、外部结果信号（用户纠正 / 重复请求 / 问答轮改动 / 执行轮零动作 / 出现真验证命令）；
- **落在哪**：`<DSH_HOME>/harness/lume-metrics.jsonl`，一行一条 JSON，可以直接看、直接删；
- **怎么看**：对话里调 `lume_metrics`，或在 DSH 的插件配置里关闭 `metrics`（关掉只是不记录，不影响任何行为）；
- **效能口径**：命中后 **3 轮**内是否出现**机械可判**的预期变化——真验证命令、或对应载具（契约 / 设计 / 台账 / 假设）从无到有；没有机械口径的机制直接标"未判定"，**不计入分母**。

两条诚实声明写在这里，也写在报表里：效能是**观察性**的，不是因果；纠正率是代理指标（用户纠正次数 / 判定次数），不是真值。样本不够时，`0/1` 可能只是"没被触发过"，不代表机制无效——它代表**还没有证据**。

## 四、长会话：上下文不是记忆的载体

- **压力预警**：上下文占用到 75% / 90% 时提醒收尾并开新会话，**先把会话记忆落盘**；
- **会话记忆**：每轮机械导出（目标 / 已拍板 / 未决 / 关键定位 / 改动与验证状态），新会话开局注入，说一句"继续"即可续接；
- **不要指望旧窗口还能继续**：宿主压缩失败时它会彻底聊不动，而会话记忆已经把该带的带走了。

### token 与缓存

Lume 每轮都往对话里加东西（模式、需求原话、台账、提醒），这些内容按"变不变"分两处放：

- **系统段**只放会话内逐字节不变的内容（人设契约、身份名、纪律）；
- **易变段**（记忆 top-k、语料示例、切换播报、本轮重点条款、提醒）交给宿主的 runtime-context 通道，渲染成对话尾部快照。

这样只有**重启、且插件本身变了**时才需要重算一次上下文；平时长对话的前缀缓存不会被每一步作废。宿主不支持 `systemPrompt.context` 时自动退回旧行为（全部挤在 system 段）——丢前缀缓存，不丢功能，启动日志会写 warn。

## 五、人设系统

人设不是"换个语气"，是换一段关系。

- **内建人设**：萝莉 `loli`（噜噜）/ 御姐 `senpai`（晚晴）/ 管家 `butler`（沈砚）/ 毒舌傲娇 `tsundere`（江野）/ 不使用人设 `none`；
- **人设蒸馏**：从聊天记录、小说、剧本、人物设定文档里提炼具名角色——语气、口头禅、回复篇幅都**锚定真实素材的统计**，而不是凭想象编；
- **语气泄漏纠偏**：内置卡带"签名词"（自称 / 称呼 / 口头禅），切换后逐轮做**纯词法**检测；检出泄漏就重开纠偏窗口，一轮干净就自动解除；
- **长期记忆**：以人设为主键，跨会话、跨项目持久；身份称呼类记忆（core）恒注入，其余按与当前消息的相关度取 top-k；
- **风格收敛**：你的纠正自动转成风格约定，你认可的回复摘录为语料，语气随使用收敛；
- **记忆星图**：把记忆与关联可视化，可筛选、可编辑、可删除；
- **角色卡导出 / 导入**：一张卡带走完整身份（记忆 + 风格 + 档案名）。

### 记忆的两类与生命周期

- **叙述与真实事件**：故事、背景、共同经历、对方身份事实、约定分别归类；叙述有 **1600 字上限**，避免人设卡被闲聊撑爆；
- **临时记忆 30 天过期**：带过期时间的记忆到点自动不再注入——"我下周出差"这类会被自然清掉，不需要你手动删；
- **同主题去重**：同一主题算同一条，相似度判重后合并，避免"换句话就多一条"；
- **蒸馏带算法版本**：角色卡记录蒸馏算法版本，升级后旧卡按新算法重蒸（启动时后台做，失败留痕）。

## 七、数据与隐私

- 数据全部在**本机**：人设与记忆、项目知识、反思、会话选择各走宿主的存储域（明文 JSON，DSH 数据目录下，可直接查看 / 备份 / 删除）；会话原文由 DSH 自己管理；
- 度量单独一条线：`<DSH_HOME>/harness/lume-metrics.jsonl`，一行一条事实；
- 插件自身**不发起网络请求**（除调用你配置的模型档做提取 / 反思 / 蒸馏）；
- 自动沉淀有**敏感内容拦截**：带值的密钥、连接串、私钥、加密串一律不入库；
- 想彻底清空：停用插件后删除上述存储域文件与 `lume-metrics.jsonl` 即可。

## 八、常见问题

**这轮它怎么没按纪律来？**
先看这一轮被归成了哪类：问答轮不会硬塞任务方法块（否则就是自相矛盾）。想让它按执行纪律走，把话说明确（"开始改"）。

**为什么工具没被调用？**
因为核心机制**不需要**它调用：改动台账、需求锚点、知识沉淀、覆盖核对都是插件自己机械完成的。模型主动调用只是补充细节。

**知识为什么没落盘？**
四种可能，日志里都能看见：① 工作目录还没拿到（新会话第一轮偶发，第二轮补上）；② 候选没通过判据（要求有证据锚点：路径 / 文件名 / 表名字段 / 命令）；③ 形状闸把它当成了代码 / 测试输出 / 表格行 / 命令行；④ 命中了敏感内容拦截。
日志关键词：`自动沉淀候选` / `项目知识补落盘` / `工作目录已解析`。

**提醒怎么变少了？**
设计如此：每个提示槽有用量上限，触发器有轮级冷却，一次只顶最紧急的一条。提醒变噪音就没人读了。

**度量里为什么是 0 和"未判定"？**
0 往往意味着**没被触发过**，不是机制失效；"未判定"是明确排除在比例外的机制（没有机械口径）。看效能要同时看命中次数——命中 0 次的比例没有意义。

**上下文快满时怎么办？**
按提醒收尾当前这一步，然后**开新会话**——会话记忆已经存好，新会话开局会带上"目标 / 已拍板 / 未决 / 关键定位"。

**换项目 / 换工作目录，知识会串吗？**
不会。项目知识按**工作目录**归属；需求特有的结论还会带"（本需求）"标记。

## 九、已知局限

**局限（不藏）**：

1. **有一部分只能真机验证**：宿主 RPC 注册、注入作用域、事件形状、装配时序——单测抓不到，所以提供了 `npm run verify:live` 把真机清单做成一条命令；门禁里的产物断言也只能保证"已知的坑不再犯"。
2. **机械判据只管"有没有证据"，管不了"判断对不对"**：语义层的对错仍在模型自己。
3. **效能是观察性的**：3 轮窗口内的共现不等于因果；样本少时读不出结论，别把 0/1 当判决。
4. **宿主侧与客户端侧同一个包**：任一侧坏了都可能让 Harness 起不来，所以门禁里有产物解析断言。
5. **旧宿主降级**：不支持 `systemPrompt.context` 的宿主会把易变段并回 system 段——丢前缀缓存，不丢功能，启动日志会写 warn。

**兼容性**：

| 项       | 说明                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------- |
| 宿主     | DSH Desktop；插件以 `dsh.bundle.patch` 声明入口，`dependencies` 为空，只声明官方包的 `peerDependencies` |
| RPC 通道 | 优先走 `connection.rpc.handle`，失败则自注册 webServer 路由（两条路径都有诊断日志）                     |
| 打包内容 | `lib/`、`cordis.patch.yml`、`assets/`、`CHANGELOG.md`（构建产物不入库，`release:check` 会先 build）     |

---

- **「讲人话」是提醒，不是门槛**：回复文本拦不住（只能在下一轮顶一句，且每会话最多一次）——它靠的是提醒 + 约束，不是机械阻断。
- **不可逆操作闸已移除**（0.8.1）：规则不写死在代码里，也不越过使用者意图（此前出现过"用户明确要求跑 `git reset --hard` 却被硬拒"）。所以**不要指望它替你拦破坏性命令**。

## 十、开发与验证

```bash
npm install --legacy-peer-deps   # DSH 生态包与若干 rc 存在 peer 冲突，需要这个开关
npm test                         # 跑全量用例（条数以当场输出为准）
npm run lint                     # 架构规则 + 类型检查 + 机制覆盖 + 格式检查
npm run build                    # 产出 lib/（构建产物不入库）
npm run release:check            # 发布门禁：对着产物断言，每条绑一个历史事故
npm run verify:live              # 真机清单（重启后跑：加载行 / 能力行 / RPC / 补蒸馏 / 知识 / 注入块）
npm run format                   # 全仓格式化
```

**三层护栏**：

- **架构规则**：分层（core 不得依赖 host / client）· ESM 扩展名 · 禁 `console.*` · 静默失败必须写理由 · 抑制必须写理由 · 类型边界（裸 `any` 只允许在装配点）· 禁 `as any` · 依赖必须真的被使用 · 文档引用必须存在；
- **机制覆盖**：从代码里枚举出全部机制（提示槽 / 触发器 / 工具 / 注入块），每一个都必须有"能跑出行为"的测试；
- **发布门禁**：对**构建产物**断言，含"客户端产物可解析""无重复顶层声明"这类一旦退化就会让 Harness 起不来的检查。

工程约定与分层原因见 [ARCHITECTURE.md](ARCHITECTURE.md)；发布流程见 [RELEASING.md](RELEASING.md)；市场登记块见 [docs/hub-registration.md](docs/hub-registration.md)；版本变更见 [CHANGELOG.md](CHANGELOG.md)。
