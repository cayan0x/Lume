# Lume · 微光

**DSH Desktop 的增强插件。两块能力：任务执行纪律，和一段能延续的关系。**

装在人设、记忆与任务协议三个位置。约束**按需注入**——闲聊轮不额外花 token。

![人设管理](docs/screenshots/manage.png)

---

## 60 秒看懂：不用 vs 用了

同一句需求：「帮我给优惠视图加个『权限人』字段，历史数据也要补」。

**不用 Lume**：模型可能先写代码再找表、改完说"已完成"但没有验证方式、跨会话换个人问就得从头讲一遍仓库约定、
上下文撑满时进度全丢、把它自己猜的口径当成你的决定。

**用了 Lume**：

- 开工前先落**任务契约**（目标 / 范围 / 数量先估 → 探索后回填 / 完成判据 / 非目标）；
- 每处改动进**改动台账**，并在交付时点出**哪几条还没验证**；
- 你需求的原话被**逐字锚定**，每一轮回显——它不会再"转述着转述着就走样"；
- 仓库约定（构建方式、列名规范、死路）**按工作目录跨会话累积**，新会话开局直接带上；
- 上下文到 75% / 90% 会提醒你收尾并开新窗口，**并把结构化记忆存好**，新会话说一句"继续"就能接上；
- 它引用没读过的代码行、对没见过的符号断言"不存在"、把两个需求数成三个、把"我没查"包装成"待你定"——**都会被当场点出来**。

## 一、任务执行纪律

### 1.1 载具：把量化与台账变成可检查的产出（6 个工具）

| 工具                  | 参数                                                                                | 用途                                                                                                  |
| --------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `lume_contract`       | `goal` / `scope` / `expectCount` / `actualCount` / `criteria` / `nonGoals` / `open` | 任务契约。**数量先估后回填**（`expectCount` 必填，估了没回填会在交付时被点出）；之后支持局部更新      |
| `lume_change`         | `target` / `change` / `why` / `verify` / `status`                                   | 改动台账：动手前先列计划项，改完推进状态；只推进状态时可只传 `target + status`                        |
| `lume_hypothesis`     | `text` / `evidence` / `status`                                                      | 假设台账（`open`/`testing`/`confirmed`/**`excluded`**）：排查类任务每验证一次就更新，已排除的别再重撞 |
| `lume_project_note`   | `kind` / `text`                                                                     | 记一条**稳定的项目事实**（按工作目录跨会话累积）：构建/测试命令、模块数据流、仓库约定、一条死路       |
| `lume_project_forget` | `id`                                                                                | 删掉一条过时/记错的项目知识（注入块里显示为 `#编号`，可点名）                                         |
| `lume_design`         | `point` / `choice` / `rejected` / `impact`                                          | 设计决策（功能型任务）：决策点 / 选择 / 被放弃的方案与理由 / 影响面；写下后跨轮回显，交付时按它对账   |

> **重要**：改动台账**不需要模型自觉**——`mutate` 类工具一被调用，插件就从入参里自动写一条（状态 `done`，标注「（自动）」）。
> 0.7.0 实测过：`lume_change` 被注入提醒 14 次、调用 0 次——所以核心机制一律**机械化**，模型调用只是补充细节。

**一次真实调用长什么样**（`lume_contract`，实现效果）：

```
lume_contract({
  goal: "优惠视图新增「权限人」字段：列表展示 + 批量导入 + 存量补数",
  scope: "WTPF_GOODS_PROPERTY_DEF 与其管理页、导入模板、存量 SQL",
  expectCount: 8,            // 先估：8 个改动点
  criteria: ["列表能看到权限人", "导入能写入", "存量已补", "回滚脚本可用"],
  nonGoals: ["不改动导入接口的既有契约", "不动需求四（有组织营销订单）"],
  open: []                   // 默认 0 个待确认——能自己核实的不许抛回来
})
```

### 1.2 触发器：按轨迹纠偏（不是按你的话）

8 个：`converge`（撒网不收敛）· `verify-as-you-go`（连写不验）· `dead-path`（死路重撞）· `contract-missing` ·
`hypothesis-stale` · `criteria-drift` · `knowledge-capture` · `design-missing`。

命中时给**验证降级阶梯**或收敛提醒；提醒只进尾部快照，**不进系统提示词**（前缀缓存不破）。

### 1.3 证据类核对（0.8.0 新增的四件）

| 核对             | 触发                                                   | 效果                                                           |
| ---------------- | ------------------------------------------------------ | -------------------------------------------------------------- |
| **引用核对**     | 回答里出现 `文件:行`，而这段本次没打开过               | 摆事实："你引用 X:159-160，本会话读过的是 412-609"             |
| **断言核对**     | 对**没见过的符号**下"没映射/不存在/不支持"这类否定断言 | 要么给出处，要么被告知"你根本没核实过它"                       |
| **需求覆盖核对** | 写出文档产物后                                         | 把**需求原句**与交付物里的句子**并列**，并点出引用不到的章节号 |
| **提问核对**     | 一轮抛出 >2 条「待你定」，或问题带"我没查/我猜"        | 要求先核实前提；**已核实的事实不许再挂成待确认**               |

### 1.4 长会话：上下文不再是记忆的载体

- **压力预警**：占用到 **75% / 90%** 时提醒"收尾并开新会话"，并**先把会话记忆落盘**；
- **会话记忆**：每轮机械导出（目标 / 已拍板 / 未决 / 关键定位 / 改动与验证状态），新会话开局注入；
- **历史补蒸馏**：启动时扫最近 7 天会话（**含已经撑满、聊不动的**）补出跨会话知识，分片执行、幂等。

### 1.5 分层注入与成本

系统提示词只放**会话恒定**内容（人设段、协议），易变内容（路由 / 台账 / 锚点 / 提醒）随**对话尾部快照**下发。

**实测**：稳态缓存命中约 **99%**；只在"重启且插件构建变化"时付一次冷启动（约 **19 万 tokens**）。
所以：**协议正文与工具 schema 的改动要攒批**——改一次就会作废整段前缀，下次重启重算。

## 二、提示槽一览

受**每会话上限**约束的槽（超上限就不再重复注入，避免刷屏式唠叨）：

| 槽                    | 上限 | 讲什么                           |
| --------------------- | ---- | -------------------------------- |
| `drift` 需求漂移      | 2    | 需求没提的变更类型被说成"我要做" |
| `citation` 引用核对   | 3    | 引用了本次没打开过的行           |
| `claim` 断言核对      | 2    | 对没见过的符号下否定断言         |
| `question` 提问核对   | 2    | 抛回的问题太多 / 没核实前提      |
| `coverage` 需求覆盖   | 2    | 需求条目与交付物的覆盖对照       |
| `pressure` 上下文压力 | 3    | 75% / 90% 预警                   |
| `carrierGap` 载具缺口 | 2    | 动了代码却没有契约/设计          |

另有一批**一次性纠偏槽**（不进上限表，命中即顶一次）：`align`（你明确纠正 / 重复提问）·
`turn` / `trigger`（轮与轨迹触发器）· `verifyFail`（红了立刻闭环）· `postTurn`（交付对账 / 载具缺口）·
`protocol`（连续失败纠偏）。

## 三、意图路由：五类分流

| 模式     | 做什么                                                        | 不做什么                                            |
| -------- | ------------------------------------------------------------- | --------------------------------------------------- |
| **问答** | 直接回答；**只读核实该做就做**（read/grep/glob/git log 允许） | 不改文件、不替你决定；**不许用「我不确定」作答**    |
| **查找** | 收集并区分已知 / 未知 / 推断；该查就查                        | 未经授权不改外部状态（文件 / 提交 / 远端 / 数据库） |
| **讨论** | 比较选项、取舍、风险                                          | 不把探讨中的方案当成已决定的执行方案                |
| **诊断** | 现象 / 证据 / 可能根因 / 验证办法                             | 不越权修复                                          |
| **执行** | 先确认目标与完成标准，再做最小变更                            | 交付时必须列"已完成 / 已验证 / 未验证 / 残留副作用" |

路由冻结在装配时（读会话权威历史），**同一轮不会自相矛盾**——这条是现场事故修出来的：曾出现"问答轮说不许调工具"
与"任务轮要求先写契约"同时注入，模型只能赌。

## 四、人设系统

**人设即人**：换人设 = 换关系，不只是换语气。

- **内建人设**：`萝莉 loli` / `御姐 senpai` / `管家 butler` / `毒舌傲娇 tsundere` / `不使用人设 none`；
- **人设蒸馏**：从**聊天记录、小说、剧本、人物设定文档**提炼具名角色——语气、口头禅、回复篇幅都**锚定真实素材统计**，不是凭想象编；
- **长期记忆与临时记忆**：以人设为主键**跨会话、跨项目**持久；有时间界限的事实自动过期；
- **风格收敛**：你的纠正自动转成风格约定；你认可的回复摘录为语料；双向反馈随使用收敛；
- **记忆星图**：记忆与关联可视化，可筛选、可编辑、可删除；
- **角色卡导出 / 导入**：一张卡带走完整身份（记忆 + 风格 + 档案名）。

![记忆星图](docs/screenshots/memory-map.png)

### 人设细节

- **两类记忆**：`narrative`（故事 / 背景，上限 1600 字）与**真实事件**（生日 / 纪念 / 共同经历 / 对方身份事实 / 约定）——
  后者靠「真实事件信号」识别，前者做长度上限，避免人设卡被闲聊撑爆；
- **临时记忆 30 天过期**：带 `expiresAt` 的记忆到点自动不再注入（`TEMPORARY_MEMORY_TTL_MS = 30 天`），
  所以「我下周出差」这类会被自然清掉，不需要你手动删；
- **记忆编号去重**（`topicKey` / `memoryId` / `isMoreSpecific`）：同一主题算同一条，精确合并；
  只有**更具体**的表述才覆盖旧的——避免「换句话就多一条」；
- **蒸馏有算法版本**：角色卡带 `DISTILL_ALGORITHM_VERSION`，升级后旧卡会按新算法重蒸（启动时后台做，失败留痕）。

人设相关工具：`lume_remember`（持久事实，每次一条、40 字内）· `lume_update_style`（风格约定）·
`lume_create_persona`（访谈收集后保存新的人设）。

## 五、安装与升级

前置：已安装 DSH Desktop。

```bash
# npm（推荐）
dsh plugin add lume-dsh-plugin

# GitHub（备选）
dsh plugin add github:cayan0x/Lume#v0.8.0

# 指定版本 / 最新
dsh plugin add lume-dsh-plugin@0.8.0
dsh plugin add lume-dsh-plugin@latest
```

**升级**：再执行一次同样的命令。若当初是**本地源码目录**安装（依赖里是 `link:`），在源码目录：

```bash
git pull && npm install --legacy-peer-deps && npm run build
```

**装完必须完全重启 DSH（含托盘进程）** —— 插件在宿主启动时加载，DSH 没有热重载。

## 七、数据与隐私

- 数据全部在**本机**：`<DSH_HOME>/harness/storages/lume_*.json`（人设 / 记忆 / 项目知识 / 反思），会话原文由 DSH 自己管理；
- 明文 JSON，**可直接查看、备份、删除**；插件自身不发起网络请求（除调用你配置的模型档做提取/蒸馏）；
- 自动沉淀有**敏感内容拦截**：带值的密钥、连接串、私钥、加密串一律不入库；
- 想彻底清空：停用插件后删除上述 `lume_*.json`。

## 八、开发与验证

```bash
npm install --legacy-peer-deps   # DSH 生态包与若干 rc 存在 peer 冲突，需此开关
npm test                         # 577 个用例
npm run lint                     # 架构 9 条规则 + 根 tsconfig 类型检查 + 机制覆盖 + prettier --check
npm run build                    # 产出 lib/（构建产物不入库）
npm run release:check            # 发布门禁：38 条对产物断言，每条绑一个历史事故
npm run verify:live              # 真机清单（重启后跑：加载行/能力行/RPC/补蒸馏/知识/注入块/客户端产物）
npm run format                   # prettier 全仓格式化
```

**工程护栏**（都是"吃过亏之后加的"）：

- **lint 9 条**：分层（core 不得依赖 host/client）· ESM 扩展名 · 禁 `console.*` · 静默失败必须带理由 ·
  抑制必须带理由 · 类型边界（裸 `any` 只在装配点）· 禁 `as any` · **依赖必须真的被使用** · **文档引用必须存在**；
- **机制覆盖**：从代码里枚举 39 个机制（提示槽 / 触发器 / 工具 / 注入块），**每个都必须有"跑出行为"的测试**；
- **门禁 38 条**：对着**产物**断言；含"客户端产物可解析""无重复顶层声明"（这两条来自一次让 Harness 起不来的事故）与"所有脚本可解析"。

工程约定与分层原因见 [ARCHITECTURE.md](ARCHITECTURE.md)；发布流程见 [RELEASING.md](RELEASING.md)；版本变更见 [CHANGELOG.md](CHANGELOG.md)。

## 九、常见问题（FAQ）

**这轮它怎么没说话 / 没有按纪律来？**
看这一轮的**模式**：问答轮不会硬塞任务方法块（否则就是自相矛盾）。想让它按执行纪律做，把话说明确（"开始改"）。

**为什么载具工具没被调用？**
因为核心机制**不需要**它调用：改动台账、需求锚点、知识沉淀、覆盖核对都是**插件自己机械完成**的。
模型调用工具只是补充细节——这也是刻意的设计（0.7.0 实测"只提醒不落地"）。

**知识为什么没落盘？**
三种可能，日志里都能看见：① 工作目录还没拿到（新会话第一轮偶发，第二轮补上）；
② 候选没通过判据（要求有证据锚点：路径/文件名/表名字段/命令）；③ 命中了敏感拦截。
日志关键词：`自动沉淀候选` / `项目知识补落盘` / `工作目录已解析`。

**上下文快满时怎么办？**
按提醒收尾当前这一步，然后**开新会话**——会话记忆已经存好，新会话开局会带上"目标 / 已拍板 / 未决 / 关键定位"，
说一句"继续"即可。**不要**指望旧窗口还能继续（宿主压缩失败时它会彻底聊不动）。

**换项目 / 换工作目录，知识会串吗？**
不会。项目知识按**工作目录**归属；需求特有的结论还会带"（本需求）"标记，只在同一需求内可见。

## 十、已知局限（不藏）

1. **只能真机验证的部分**：宿主 RPC 注册、注入作用域、事件形状、装配时序——单测抓不到，所以才有 `npm run verify:live`
   把清单做成一条命令；`lib/` 里的产物断言也只能保证"已知的坑不再犯"。
2. **评审可测的地方严丝合缝，测不到的地方靠自觉**：比如"这个判断对不对"属于语义层，机械判据只能管"有没有证据"。
3. **客户端产物与插件同版本号**：同一个包同时装宿主侧与客户端侧，任一侧坏了都可能让 Harness 起不来（所以门禁有产物解析断言）。
4. **旧版本宿主降级**：不支持 `systemPrompt.context` 的宿主（0.1.5 之前）会把易变段并回 system 段——丢前缀缓存，不丢功能，启动日志会写 warn。
