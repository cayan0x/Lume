# Lume · 微光

**给 DSH Desktop 加一层工程纪律，和一个能延续下去的人设。**

Lume 管两件不搭界的事。一件是任务：约束模型"怎么把活干完"——先想清楚再动手、改一处验一处、交付前对账。另一件是人设：塑造它"用什么风格跟你说话"——从素材里蒸馏具名角色，长期记忆随对话演进。

纪律层对所有会话生效，包括你选了"不使用人设"的时候。人设只影响自然语言表达，不介入代码、命令与工具调用的结果。

---

## 它解决什么问题

同一个需求：「帮我给优惠视图加个『权限人』字段，历史数据也要补」。

**没有 Lume**：它先动手改了代码。你问"表结构对过吗"，它说"已确认"——但它根本没打开过那张表。这一轮聊完你去开会，回来换个窗口继续，它又要你从头讲一遍这个仓库怎么跑。上下文撑满以后，进度就留在了那个窗口里。

**有 Lume**：

- 开工前把你的原话**逐字**记下来，并落一份契约：目标、范围、**数量先估**（探索后回填实际值）、完成判据、非目标；
- 要改哪张表，就得先打开它——**没读过就动手，会被点出来**；
- 每处改动自动进台账，交付时把**还没验证的条目**列出来，而不是说一句"已完成"；
- 它引用了没打开过的代码行、对没见过的符号断言"不存在"、把两个需求数成三个、把"我没查"包装成"待你定"——都会被当场点出来；
- 换个窗口说一句"继续"，它带上目标、已拍板、未决、关键定位接着干。

**它不做的事**：

- 不偷偷改文件——问答轮不改文件，诊断轮不越权修复，只有执行轮才动状态；
- 不发起网络请求——除了调用你自己配置的模型档做记忆提取与人设蒸馏；
- 不给闲聊加固定开销——协议是按需注入的，闲聊聊几句不会背上整份工作协议的成本；
- 不替你做决定——把选择权交回你之前，它得先核实问题本身是否成立。

## 安装与升级

前置：已安装 DSH Desktop。

```bash
# npm（推荐）
dsh plugin add lume-dsh-plugin

# GitHub（备选）
dsh plugin add github:cayan0x/Lume#v0.8.0

# 指定版本 / 最新
dsh plugin add lume-dsh-plugin@0.8.0
dsh plugin add lume-dsh-plugin@latest
```

**升级**：重复执行同一条命令即可。若当初是用**本地源码目录**装的（依赖里是 `link:`），在源码目录执行：

```bash
git pull && npm install --legacy-peer-deps && npm run build
```

**装完必须完全重启 DSH（含托盘进程）**——插件在宿主启动时加载，DSH 没有热重载。

## 一、任务执行纪律

### 1.1 载具：把"量化"和"台账"变成能检查的产出

模型丢的通常不是"不知道要量化"，而是**没有一个地方放量化结果**。Lume 给它六个可调用的工具：

| 工具                  | 做什么                                                    |
| --------------------- | --------------------------------------------------------- |
| `lume_contract`       | 任务契约：目标 / 范围 / 数量 / 完成判据 / 非目标 / 待确认 |
| `lume_change`         | 改动台账：每处改动改了什么、为什么、**怎么验证的**        |
| `lume_hypothesis`     | 假设台账：含**已排除项**，被推翻的假设也留档，避免重撞    |
| `lume_project_note`   | 记一条稳定的项目事实（按工作目录跨会话累积）              |
| `lume_project_forget` | 删掉一条过时或记错的项目知识                              |
| `lume_design`         | 设计决策：决策点 / 选择 / 放弃的方案与理由 / 影响面       |

一段真实的契约长这样：

```
lume_contract({
  goal: "优惠视图新增「权限人」字段：列表展示 + 批量导入 + 存量补数",
  scope: "WTPF_GOODS_PROPERTY_DEF 与其管理页、导入模板、存量 SQL",
  expectCount: 8,            // 先估：8 个改动点，探索后回填实际值
  criteria: ["列表能看到权限人", "导入能写入", "存量已补", "回滚脚本可用"],
  nonGoals: ["不改动导入接口的既有契约", "不动需求四（有组织营销订单）"],
  open: []                   // 默认 0 个待确认——能自己核实的不许抛回来
})
```

**改动台账不需要模型自觉**：`mutate` 类工具一被调用，插件就从入参里自动记一条（标注"（自动）"）。需求锚点、项目知识、覆盖核对同样是插件机械完成的。

这是刻意的取舍：只靠提醒的机制会退化成"提醒了很多次，一次都没落地"。所以核心机制一律自动化，模型调用工具只是为了补充细节。

### 1.2 触发器：按轨迹纠偏，不看你怎么说

八种情况会被识别出来：撒网不收敛、连写不验、死路重撞、该写契约却没写、假设过期没更新、判据随进展漂移、该记的知识没记、该做设计却直接动手。

命中时给一条**验证降级阶梯**或收敛提醒，而不是泛泛地要求"要有验证"。提醒只进对话尾部，不进系统提示词——既不打断你，也不作废缓存。

### 1.3 证据类核对

| 核对             | 什么时候响                                             | 你会看到什么                                         |
| ---------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| **引用核对**     | 回答里写了 `文件:行`，但这段本次没打开过               | 摆出事实：你引用的位置，本会话读过的范围是哪儿       |
| **断言核对**     | 对没见过的符号下"没映射 / 不存在 / 不支持"这类否定断言 | 要么给出处，要么被告知"你没核实过它"                 |
| **需求覆盖核对** | 写出文档产物之后                                       | 把需求原句与交付物里的句子并列，点出引用不到的章节号 |
| **提问核对**     | 一轮抛出超过 2 条「待你定」，或问题带着"我没查 / 我猜" | 要求先核实前提；已核实的事实不许再挂成待确认         |

### 1.4 长会话：上下文不是记忆的载体

- **压力预警**：上下文占用到 75% / 90% 时提醒你收尾并开新会话，**先把会话记忆落盘**；
- **会话记忆**：每轮机械导出（目标 / 已拍板 / 未决 / 关键定位 / 改动与验证状态），新会话开局注入；
- **历史补蒸馏**：启动时扫最近 7 天的会话（**包括已经撑满、聊不动的那些**）补出跨会话知识，分片执行、幂等不重复。

### 1.5 token 与缓存

Lume 每轮都会往对话里加东西：当前模式、需求原话、台账、提醒。这些内容分两处放——不变的（人设段、协议）进系统提示词，会变的贴在对话末尾。

这样长对话的缓存不会被反复作废：只有**重启、且插件本身变了**的时候，才需要重算一次上下文（约 19 万 tokens）。所以协议正文与工具 schema 的改动是攒批发版、一起重启的。

## 二、人设系统

人设不是"换个语气"，是换一段关系。

- **内建人设**：萝莉 `loli` / 御姐 `senpai` / 管家 `butler` / 毒舌傲娇 `tsundere` / 不使用人设 `none`；
- **人设蒸馏**：从聊天记录、小说、剧本、人物设定文档里提炼具名角色——语气、口头禅、回复篇幅都**锚定真实素材的统计**，而不是凭想象编；
- **长期记忆**：以人设为主键，跨会话、跨项目持久；
- **风格收敛**：你的纠正自动转成风格约定，你认可的回复摘录为语料，语气随使用收敛；
- **记忆星图**：把记忆与关联可视化，可筛选、可编辑、可删除；
- **角色卡导出 / 导入**：一张卡带走完整身份（记忆 + 风格 + 档案名）。

### 记忆的两类与生命周期

- **叙述（narrative）与真实事件**：故事、背景、共同经历、对方身份事实、约定分别归类；叙述有 **1600 字上限**，避免人设卡被闲聊撑爆；
- **临时记忆 30 天过期**：带过期时间的记忆到点自动不再注入——"我下周出差"这类会被自然清掉，不需要你手动删；
- **同主题去重**：同一主题算同一条，精确合并；只有**更具体**的表述才覆盖旧的，避免"换句话就多一条"；
- **蒸馏带算法版本**：角色卡记录蒸馏算法版本，升级后旧卡按新算法重蒸（启动时后台做，失败留痕）。

### 人设工具

`lume_remember`（记一条持久事实，每次一条、40 字内）· `lume_update_style`（固化一条风格约定）· `lume_create_persona`（访谈收集后保存一个新的人设）。

## 三、配置

在 DSH 的插件配置里改（键名与 `src/index.ts` 的配置 schema 一致）：

| 配置                                     | 默认       | 说明                                                           |
| ---------------------------------------- | ---------- | -------------------------------------------------------------- |
| `layeredInjection`                       | `true`     | 分层注入；关掉则易变内容回到 system 段（丢前缀缓存，不丢功能） |
| `projectMemory`                          | `true`     | 跨会话项目知识与载具台账                                       |
| `behaviorTriggers`                       | `true`     | 行为触发器（按轨迹纠偏）                                       |
| `memoryInjection`                        | `true`     | 长期记忆注入                                                   |
| `styleInjection`                         | `true`     | 风格约定注入                                                   |
| `reflectionEnabled`                      | `true`     | 会话结束的反思回环（评分与跳过原因都会留痕）                   |
| `extractionProvider` / `extractionModel` | 回落主对话 | 记忆提取专用模型档（可只配其一）                               |
| `distillProvider` / `distillModel`       | 回落主对话 | 人设蒸馏专用模型档（可只配其一）                               |

## 四、数据与隐私

- 数据全部在**本机**：`<DSH_HOME>/harness/storages/lume_*.json`（人设 / 记忆 / 项目知识 / 反思），会话原文由 DSH 自己管理；
- 明文 JSON，**可以直接查看、备份、删除**；插件自身不发起网络请求（除调用你配置的模型档做提取 / 蒸馏）；
- 自动沉淀有**敏感内容拦截**：带值的密钥、连接串、私钥、加密串一律不入库；
- 想彻底清空：停用插件后删除上述 `lume_*.json` 即可。

## 五、常见问题

**这轮它怎么没按纪律来？**
先看这一轮被归成了哪类：问答轮不会硬塞任务方法块（否则就是自相矛盾）。想让它按执行纪律走，把话说明确（"开始改"）。

**为什么载具工具没被调用？**
因为核心机制**不需要**它调用：改动台账、需求锚点、知识沉淀、覆盖核对都是插件自己机械完成的。模型主动调用只是补充细节。

**知识为什么没落盘？**
三种可能，日志里都能看见：① 工作目录还没拿到（新会话第一轮偶发，第二轮补上）；② 候选没通过判据（要求有证据锚点：路径 / 文件名 / 表名字段 / 命令）；③ 命中了敏感内容拦截。
日志关键词：`自动沉淀候选` / `项目知识补落盘` / `工作目录已解析`。

**上下文快满时怎么办？**
按提醒收尾当前这一步，然后**开新会话**——会话记忆已经存好，新会话开局会带上"目标 / 已拍板 / 未决 / 关键定位"，说一句"继续"即可。不要指望旧窗口还能继续：宿主压缩失败时它会彻底聊不动。

**换项目 / 换工作目录，知识会串吗？**
不会。项目知识按**工作目录**归属；需求特有的结论还会带"（本需求）"标记，只在同一需求内可见。

## 六、已知局限与兼容性

**局限（不藏）**：

1. **有一部分只能真机验证**：宿主 RPC 注册、注入作用域、事件形状、装配时序——单测抓不到，所以提供了 `npm run verify:live` 把真机清单做成一条命令；门禁里的产物断言也只能保证"已知的坑不再犯"。
2. **机械判据只管"有没有证据"，管不了"判断对不对"**：语义层的对错仍在模型自己。
3. **宿主侧与客户端侧同一个包**：任一侧坏了都可能让 Harness 起不来，所以门禁里有产物解析断言。
4. **旧宿主降级**：不支持 `systemPrompt.context` 的宿主会把易变段并回 system 段——丢前缀缓存，不丢功能，启动日志会写 warn。

**兼容性**：

| 项       | 说明                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------- |
| 宿主     | DSH Desktop；插件以 `dsh.bundle.patch` 声明入口，`dependencies` 为空，只声明官方包的 `peerDependencies` |
| RPC 通道 | 优先走 `connection.rpc.handle`，失败则自注册 webServer 路由（两条路径都有诊断日志）                     |
| 打包内容 | `lib/`、`cordis.patch.yml`、`assets/`、`CHANGELOG.md`（构建产物不入库，`release:check` 会先 build）     |

## 七、开发与验证

```bash
npm install --legacy-peer-deps   # DSH 生态包与若干 rc 存在 peer 冲突，需要这个开关
npm test                         # 616 个用例（以当场输出为准）
npm run lint                     # 架构规则 + 类型检查 + 机制覆盖 + 格式检查
npm run build                    # 产出 lib/（构建产物不入库）
npm run release:check            # 发布门禁：对着产物断言，每条绑一个历史事故
npm run verify:live              # 真机清单（重启后跑：加载行 / 能力行 / RPC / 补蒸馏 / 知识 / 注入块）
npm run format                   # 全仓格式化
```

**三层护栏**：

- **架构规则**：分层（core 不得依赖 host/client）· ESM 扩展名 · 禁 `console.*` · 静默失败必须写理由 · 抑制必须写理由 · 类型边界（裸 `any` 只允许在装配点）· 禁 `as any` · 依赖必须真的被使用 · 文档引用必须存在；
- **机制覆盖**：从代码里枚举出全部机制（提示槽 / 触发器 / 工具 / 注入块），每一个都必须有"能跑出行为"的测试；
- **发布门禁**：对**构建产物**断言，含"客户端产物可解析""无重复顶层声明"这类一旦退化就会让 Harness 起不来的检查。

工程约定与分层原因见 [ARCHITECTURE.md](ARCHITECTURE.md)；发布流程见 [RELEASING.md](RELEASING.md)；版本变更见 [CHANGELOG.md](CHANGELOG.md)。
