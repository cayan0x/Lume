# `lume_patch` 对照实验（A/B）：两层，别一锅煮

> 目的：回答两个**不同**的问题，所以拆成两层各管一件事。
> **不验证「更像 Codex」**——DeepSeek 没在 V4A 语法上训过，那是要被证伪的假设，不是卖点。

## 第一层：解析层（离线，不跑 agent）——已实现

**问的是**：工具本身准不准。

- **跑法**：`npx vitest run test/patch-cases.test.ts`（**25 个 case，秒级**，共 5 类题型；已进单测当回归）。
- **三种结果**：①命中（且改在**正确位置**）②拒绝（多解/找不到/格式错）③**改错位置**（断言必须失败）。
- **题型**（都是真实失败面）：同一段文本出现两次 / 缩进·CRLF 不一致 / 补丁少一行上下文 / 跳段插入 / 整函数替换。
- **两个已知代价被显式锁成断言**（不藏在注释里）：
  1. 降级命中（rstrip/trim）时替换文本是**补丁自己写的行**——补丁没带的缩进会丢（与 Codex 同语义）；
  2. 多解一律拒绝（不取第一个），代价是模型要补上下文重试。

## 第二层：agent 层（真机 A/B）——只回答解析层答不了的问题

**问的是**：模型会不会用这个语法。

- **样本**：8–10 个**真任务**（不是玩具题），配对跑：同一需求，一遍 `edit`、一遍 `lume_patch`，**中间 `git` 复位**。
- **记四个数**：一次改对率 / 重试次数 / token / **有没有改错地方**。
- **旁证**：探针 `node scripts/probe.mjs read` 看 `tools/pre-execute (lume_patch)` 与 `fs/observed` 的出现次数。

## 判定门槛（已按实际改宽）

原门槛写的是「F4 与 token 都不优于 `edit` 就不上线」——那等于要求两项**同时严格更优**，几乎不可能达到：
补丁工具的准确率未必比 `edit` 高，省 token 只在「多处机械改动」这类题型上才明显。改为：

1. **F4（需二次修补）不低于 `edit`**；
2. **token 明显更省（≥20%）**；
3. **分题型给结论**——例如「多文件机械替换」赢、「单行小改」平，**这就够了**，不必强求全面压制。

任一门槛不满足就不上线；只在子集占优就把它**限定成那个子集的工具**（也是结论，不是失败）。

## 失败态口径（两层共用）

| 代号 | 含义 |
| --- | --- |
| **F0** | 一次改对 |
| **F1** | 匹配失败（锚点找不到，模型得重给上下文） |
| **F2** | **多解拒绝**（我们主动拒绝——设计代价，单独计） |
| **F3** | 补丁语法错 |
| **F4** | 需二次修补（改完还要再改一次才成立） |

> ⚠️ 开跑前置：先确认探针 `fsSeam` 六行里 `resolve/stat/readText` 都是 `function`
> （见 `docs/design/lume-patch-and-delivery-gate.md` §6 与 `.goose/state.md` 最新一节）——
> 否则实验会浪费在一个第一次调用就报错的工具上。

## 实测结果（2026-09-25 · 4 件事 × 2 遍，模型 deepseek-v4-flash / standard，全程同一工作区）

| 任务 | 用 edit | 用 lume_patch | 新工具 |
| --- | --- | --- | --- |
| t1 [S] 2 处小改 | 30,364 token · 5 次调用 · 30.6s | 23,877 · 4 次 · 19.3s | 省 21.4% |
| t2 [M] 改名 3 处 + 常量 | 29,741 · 5 次 · 25.5s | 32,313 · 8 次 · 46.3s | **贵 8.6%** |
| t3 [M] 早退 + off-by-one | 26,818 · 5 次 · 19.3s | 24,726 · 4 次 · 19.5s | 省 7.8% |
| t4 [L] **三文件六处替换** | 33,934 · **16 次** · 28.1s | 33,565 · **16 次** · 27.0s | 省 1.1% |
| **合计** | **120,857 · 31 次 · 103.5s** | **114,481 · 32 次 · 112.1s** | **省 5.3%** |

**准确率：4/4 对 4/4（8 遍全对，两个工具都没有翻车）。**

### 判定：**不通过**

- ① F4 不低于 edit：**满足**（0 vs 0，谁都没需要二次修补）
- ② token 省 ≥20%：**不满足**（实测 5.3%）
- ③ 分题型：**无稳定优势**（t1 省 21%、t2 贵 8.6%、t4 几乎持平）

按事先定好的规矩：**不通过就不上线、不设默认**——`lume_patch` 保留为**可选工具**（它在工具层确实把"三次 edit"压成"一次调用"，见 t4 的调用序列），
但不作为默认写路径、不写进任何"必须用它"的纪律。**不许事后改口径**：「感觉更快」不作为证据（t1 那次 −21% 很可能是"本实验第一个会话、全量冷启动"造成的顺序偏差；
我们随后做了顺序平衡——t3/t4 改成新工具先跑——t4 的差距就归零，这与顺序偏差的解释一致）。

### 本轮真正的发现（比工具本身值钱）

1. **成本大头不是"怎么改文件"，是记账**：全部 63 次工具调用里 **20 次是 Lume 自己的 `lume_*`**（t4 两条各自 5 次：`lume_contract` + `lume_design` + `lume_change`×3）。
   工具层省下的那 2 次 edit，被记账和重复回读吃掉了。
2. **重复回读**：t4 两条各自 `read` 了 **6 次**（每个文件改前、改后各一次）——这是"验证纪律"的代价，也是 t4 成本与 t1 差不多两倍的主因。
3. **模型确实会用这个语法**：第 2 条首次试用就写出正确的 V4A（同一 `@@` 段两处 `-/+`），全程零报错、零重试；t4 一条 `lume_patch` 改完三个文件也成功。
   → 之前"DeepSeek 没训过 V4A 会翻车"的担心**被证伪**（在 4 类题型上）。

### 因此下一步的优先级改变

- **先做记账瘦身**（合并/按任务类型关闭 `lume_change`/`lume_contract`/`lume_design`），它占 32% 的调用量——比继续打磨补丁语法值钱得多。
- **再想"重复回读"**：把"改完每文件回读"改成"一个任务收尾回读一次"。
- 若还要再验 `lume_patch`，应当在**关掉记账**的条件下跑（隔离变量），否则测的还是记账。
