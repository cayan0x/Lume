### 假设台账验收（2026-09-25 · 三次重启后通过）

| 轮次 | 结果 | 根因（已修） |
| --- | --- | --- |
| 1 | ✗ | 闸门挂 `verifyFailStreak >= 2`，而真机失败被判成 `unknown`（PowerShell 管道吞退出码）→ 计数器恒 0 |
| 2 | ✗ | `FAILURE_RE` 的 `\berror\b` **匹配不到 `AssertionError`**（词边界）→ 失败被判成**成功** |
| 3 | ✓ | `自动入账假设（第 1 次非成功）` + `hypotheses` 0 → 1 + h1 全绿 |

**修法**：①「任何非成功结果都入账」，「第几次」从台账本身数（不信易失计数器）②`FAILURE_RE` 增补 `AssertionError / ERR_ASSERTION / exit code [1-9] / ✗`（**刻意不加** `failing/failures`：成功输出里常有 "0 failures"）。

**连带影响（重要）**：`looksLikeFailure` 是所有「红了要不要立刻闭环」机制（验证结算、死路提示、增量验证、交付门槛）的共同判据——修好后**若干长期不响的机制可能开始响**，接下来几天应盯 `harness.log` 里的新字样。

**对"是否已接近完善"的回答**：功能面确实饱和了；但这次体检只用了几条查询就查出**一个完整的死机制**、**一个被宿主遮挡的触发器**、**一个真实使用为 0 的工具**。也就是说——**"有效性"这一面才刚开始查，而且它就是下一步该做的事**：不是加功能，是**把没用的机制删掉**。
